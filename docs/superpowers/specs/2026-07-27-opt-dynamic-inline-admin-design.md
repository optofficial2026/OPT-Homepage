# OPT 동적 콘텐츠 및 인라인 관리자 편집 설계

## 1. 목표

기존 OPT 홈페이지의 디자인, 공개 페이지 구조, 애니메이션, 필터 동작을 유지하면서 운영자가 현재 화면에서 모집 상태, 홈페이지 지표, 연혁, 활동 기록, 세미나 자료, 해커톤 결과물을 관리할 수 있게 한다.

프론트엔드는 GitHub Pages에 배포하고, 관리자 인증·데이터베이스·썸네일 저장은 Supabase 무료 플랜을 사용한다. 별도 관리자 페이지는 만들지 않는다.

## 2. 확정된 제약

- 기존 홈(`/`), 활동 기록(`/log/`), 아카이브(`/archive/`) 화면과 시각 체계를 유지한다.
- 일반 방문자에게 관리자 UI를 노출하지 않는다.
- 관리자는 현재 페이지에서 편집 모드를 켜고 해당 섹션을 직접 관리한다.
- 공개 회원가입은 제공하지 않는다. 관리자 계정은 Supabase에서 수동으로 생성한다.
- 모집 진입 모달은 만들지 않는다.
- 대용량 PPT, PDF, ZIP 파일은 Supabase Storage에 직접 저장하지 않고 외부 자료 URL을 연결한다.
- Supabase Storage에는 압축된 썸네일만 저장한다.
- 사이트는 GitHub Pages 기본 주소로 먼저 배포하고, 추후 `opt.it.kr` 사용자 지정 도메인을 연결할 수 있어야 한다.
- 관리자 작업 주기는 짧으면 한 달, 길면 약 6개월로 가정한다.
- 해커톤 상세 화면은 사용자가 제공한 `OPT Hackathon Detail.html`의 레이아웃, 콘텐츠 순서, 시각 체계를 구현 기준으로 사용한다.
- 활동 기록 카드, 세미나 자료 행, 해커톤 카드를 선택하면 각각 상세 화면을 표시한다.

## 3. 선택한 접근 방식

현재 공개 페이지 위에 관리자 전용 편집 기능을 조건부로 추가한다.

푸터에 작은 `관리자 로그인` 진입점을 둔다. 로그인 성공 후에만 관리자 도구 모음과 섹션별 `수정`, `추가`, `삭제` 버튼이 렌더링된다. 편집 폼은 별도 관리자 화면 대신 네이티브 `<dialog>`를 사용한다.

이 방식은 공개 화면을 복제하지 않고 기존 컴포넌트와 데이터 흐름을 그대로 재사용한다. 일반 방문자의 DOM에는 관리자 버튼과 편집 폼을 렌더링하지 않는다.

## 4. 시스템 구조

### 4.1 GitHub Pages

- 현재 React/Vite 멀티페이지 애플리케이션을 정적 파일로 제공한다.
- GitHub Actions가 테스트, 타입 검사, 빌드, Pages 배포를 실행한다.
- GitHub Pages 기본 경로와 사용자 지정 도메인에서 모두 동작하도록 Vite base 경로를 배포 환경값으로 관리한다.
- 내부 링크와 정적 자산 경로는 `import.meta.env.BASE_URL`을 기준으로 생성한다.

### 4.2 Supabase

- Auth: 관리자 이메일·비밀번호 로그인과 세션 관리
- Postgres: 공개 콘텐츠와 사이트 설정 저장
- Storage: 공개 웹 이미지 저장
- Row Level Security: 공개 읽기와 관리자 쓰기 권한 분리

브라우저에는 Supabase publishable key만 제공한다. secret key 또는 service role key는 저장소, 빌드 결과물, 브라우저에 포함하지 않는다.

## 5. 관리자 인증과 권한

Supabase 프로젝트와 최초 관리자 계정은 개인 학회원 계정이 아닌 OPT 공식 계정으로 생성·소유한다. 공식 계정의 이메일, 비밀번호, 복구 정보는 저장소나 프론트엔드 환경 변수에 기록하지 않는다. 관리자 사용자는 Supabase 대시보드에서 수동 생성하며 공개 가입, 관리자 초대 화면, 비밀번호 초기화 관리 화면은 초기 범위에서 제외한다.

관리자 권한은 Auth 사용자의 UUID가 `admin_profiles.user_id`에 등록되어 있는지로 판단한다. 이메일, `user_metadata`, 브라우저 저장소 값은 권한 판정에 사용하지 않는다.

RLS 정책은 다음 원칙을 따른다.

- `anon`, `authenticated`: 공개 콘텐츠 조회 가능
- `authenticated` 관리자: 모든 콘텐츠 조회 및 추가·수정·삭제 가능
- 비관리자 로그인 사용자: 쓰기 불가
- Storage 공개 버킷: 콘텐츠 이미지 조회 가능
- Storage 쓰기: 관리자만 가능

클라이언트의 버튼 숨김은 편의 기능일 뿐 보안 경계로 사용하지 않는다. 실제 쓰기 차단은 Postgres와 Storage RLS에서 수행한다.

## 6. 관리자 편집 경험

### 6.1 로그인 전

- 일반 방문자 UI는 현재 모습과 동일하다.
- 푸터에 작은 `관리자 로그인` 링크만 추가한다.
- 로그인 폼은 네이티브 `<dialog>`로 표시한다.

### 6.2 로그인 후

페이지 상단에 관리자 도구 모음을 표시한다.

- `편집 모드 켜기/끄기`
- `모집 중/모집 종료` 전환
- `로그아웃`

편집 모드를 켰을 때만 현재 페이지의 관련 섹션에 편집 버튼을 표시한다.

- 홈 Hero: `지표 수정`
- 모집 배너: `모집 정보 수정`
- 연혁: `연혁 추가`, 항목별 `수정`, `삭제`
- 활동 기록: `글 작성`, 항목별 `수정`, `삭제`
- 아카이브: `자료 추가`, 항목별 `수정`, `삭제`
- 활동·세미나·해커톤 상세: `내용 수정`, `대표 이미지 교체`, 갤러리 이미지 `추가·교체·삭제`

삭제는 대상 제목을 포함한 확인 대화상자를 한 번 거친다. 저장 중에는 중복 제출을 막고, 성공 후 공개 목록을 다시 조회한다. 저장 실패 시 기존 화면 데이터를 유지하고 오류 메시지를 표시한다.

## 7. 모집 모드

### 7.1 모집 중

- 상단 모집 티커 표시
- Hero 모집 배지 표시
- 네비게이션 모집 지원 버튼 표시
- 하단 모집 배너 표시
- 유효한 폼 URL이 있을 때만 지원 링크 활성화

관리자는 다음 값을 수정할 수 있다.

- 모집 기수
- 티커 문구
- Hero 모집 배지 문구
- 하단 배너 제목
- 하단 배너 설명
- 지원 폼 URL

### 7.2 모집 종료

- 상단 모집 티커 숨김
- Hero 모집 배지 숨김
- 네비게이션 지원 버튼 숨김
- 모집 진입 모달 없음
- 하단 배너는 유지
- 하단 배너에 `현재 모집 중이 아닙니다. 다음 기수 모집 때 다시 찾아주세요.` 표시
- 지원 링크 숨김

## 8. 홈페이지 지표

관리자는 다음 정수 값을 수정한다.

- 활동 기수
- 활동 인원
- 활동 프로그램 수

DB에는 0 이상의 정수만 저장하고 화면에서는 항상 `숫자+` 형식으로 표시한다. 예시는 `1+`, `11+`, `4+`이다. 빈 값, 음수, 소수, 숫자가 아닌 값은 저장하지 않는다.

기존 count-up 애니메이션을 유지하며, DB에서 받은 정수를 애니메이션 목표값으로 사용한다.

## 9. 활동 연혁

연혁 항목은 날짜, 제목, 설명으로 구성한다.

- 관리자는 추가·수정·삭제할 수 있다.
- `occurred_on` 내림차순으로 조회해 최신 항목을 위에 둔다.
- 별도 수동 정렬 기능과 `sort_order`는 만들지 않는다.
- 연혁 컨테이너에는 최대 높이와 `overflow-y: auto`를 적용한다.
- 페이지 진입과 데이터 갱신 시 스크롤 위치를 맨 위로 둔다.
- 기존 타임라인의 색상, 선, 점, 글꼴, 간격은 유지한다.

## 10. 활동 기록

활동 기록은 기존 카드 그리드와 기수·분류 필터를 유지한다.

각 글은 다음 필드를 가진다.

- URL 식별자
- 기수
- 분류: `STUDY`, `SEMINAR`, `EVENT`
- 날짜
- 제목
- 요약
- 본문
- 선택적 썸네일
- 공개 여부
- 생성·수정 시각

관리자는 현재 `/log/` 페이지에서 글을 작성하고 수정한다. 공개 카드를 선택하면 동일한 페이지에서 `/log/?id=<slug>` 쿼리 파라미터를 사용해 상세 본문을 표시한다. 별도 HTML 진입점이나 새로운 라우터 의존성은 추가하지 않는다.

활동 기록 상세 화면은 기존 네비게이션과 푸터 사이에 다음 순서로 표시한다.

1. 활동 기록 목록으로 돌아가기
2. 분류, 기수, 날짜
3. 제목과 한 줄 요약
4. 대표 이미지
5. 상세 본문
6. 선택적 활동 이미지
7. 선택적 관련 자료 링크

목록으로 돌아갈 때 기존 분류·기수 필터와 스크롤 위치를 복원한다.

본문은 초기 버전에서 일반 텍스트와 줄바꿈만 지원한다. 리치 텍스트 에디터와 임의 HTML 입력은 보안·운영 복잡도가 커서 제외한다.

## 11. 아카이브

기존 세미나 리스트와 해커톤 카드 구성을 유지한다. 하나의 `archive_items` 테이블에서 `kind` 값으로 구분한다.

### 11.1 세미나 자료

- 종류: `seminar`
- 기수
- 날짜
- 자료 유형: `SLIDE`, `NOTE`
- 제목
- 자료 소개
- 선택적 대표 이미지
- 선택적 발표자·작성자
- 선택적 핵심 키워드
- 선택적 주요 내용
- 선택적 자료 URL
- 공개 여부

세미나 자료 행을 선택하면 `/archive/?id=<slug>`에서 상세 화면을 표시한다. 상세 화면은 목록으로 돌아가기, 자료 유형·기수·날짜, 제목, 발표자·작성자, 대표 이미지, 자료 소개, 주요 내용, 키워드, 자료 열기 링크 순서로 구성한다. 자료 URL이 있을 때만 `자료 열기` 링크를 표시한다.

### 11.2 해커톤 결과물

- 종류: `hackathon`
- URL 식별자
- 기수
- 진행 시작일·종료일
- 프로젝트명
- 한 줄 소개
- 선택적 수상 결과
- 대표 썸네일
- 해결하려는 문제
- 해결 방법
- 핵심 기능 목록
- 프로젝트 이미지 목록
- 개발 과정 목록
- 시스템 구성 설명
- 회고
- 선택적 결과 요약
- 기술 스택 문자열 배열
- 선택적 팀명과 팀원·역할 목록
- 선택적 GitHub URL
- 선택적 데모 URL
- 선택적 발표자료 URL
- 공개 여부

해커톤 카드를 선택하면 `/archive/?id=<slug>`에서 사용자가 제공한 `OPT Hackathon Detail.html` 디자인을 따른 상세 화면을 표시한다.

화면 순서는 다음과 같다.

1. 해커톤 목록으로 돌아가기
2. `HACKATHON`, 기수, 기간, 선택적 수상 배지
3. 프로젝트명과 한 줄 소개
4. 대표 썸네일
5. 해결하려는 문제와 해결 방법
6. 번호가 있는 핵심 기능 목록
7. 프로젝트 이미지 갤러리
8. 개발 과정
9. 시스템 구성
10. 회고와 선택적 결과 카드
11. 기술 스택
12. 선택적 팀명과 팀원·역할
13. 존재하는 GitHub·데모·발표자료 링크

공개 상태에서는 HTML 시안의 `Replace`, `Edit` 컨트롤을 렌더링하지 않는다. 관리자 로그인 후 편집 모드를 켠 경우에만 동일한 위치에 이미지 교체와 섹션 수정 컨트롤을 표시한다. 링크가 없는 버튼이나 가짜 자료 링크는 렌더링하지 않는다.

## 13. 이미지 정책

- Storage 버킷 이름: `content-media`
- 허용 형식: JPEG, PNG, WebP
- 파일당 최대 크기: 5MB
- 활동·해커톤 상세 화면은 대표 이미지 1개와 선택적 갤러리 이미지를 지원한다.
- 동일 경로 덮어쓰기 대신 새 고유 경로 생성
- 새 썸네일 저장 성공 후 DB 레코드 갱신
- 레코드 저장 실패 시 새로 올린 파일 제거 시도
- 기존 썸네일 교체 성공 후 사용하지 않는 이전 파일 제거

PPT, PDF, ZIP, 동영상은 직접 업로드하지 않고 URL만 저장한다.

## 14. 데이터 로딩과 장애 대응

공개 페이지는 다음 우선순위로 콘텐츠를 표시한다.

1. Supabase에서 성공적으로 조회한 최신 공개 데이터
2. 브라우저에 저장된 마지막 성공 데이터
3. 현재 `src/data/content.ts`에 포함된 기본 데이터

Supabase가 휴면 또는 일시 장애 상태여도 공개 페이지가 빈 화면이 되지 않아야 한다. 캐시 데이터에는 버전과 저장 시각을 포함하고, 스키마 버전이 맞지 않으면 폐기한다.

관리자 쓰기 작업은 Supabase 연결이 정상일 때만 허용한다. 실패한 저장을 성공한 것으로 표시하지 않는다.

무료 프로젝트 휴면을 우회하기 위한 불필요한 자동 커밋, 자체 서버, 복잡한 동기화 시스템은 만들지 않는다. 휴면 상태에서는 운영자가 Supabase 대시보드에서 프로젝트를 재개한다.

## 15. GitHub Pages 배포와 도메인

GitHub Actions는 `main` 브랜치 변경 시 다음 순서로 실행한다.

1. 의존성 설치
2. 테스트
3. TypeScript 검사
4. Vite 빌드
5. Pages artifact 업로드
6. GitHub Pages 배포

도메인 구매 전에는 저장소 하위 경로를 base로 사용한다. `opt.it.kr` 구매 후에는 Pages 사용자 지정 도메인을 연결하고 base를 `/`로 바꾼다. Supabase Auth의 허용 URL과 로그인 redirect URL에도 실제 운영 주소를 등록한다.

## 16. 검증 전략

### 16.1 첫 번째 시행: 기능

- 모집 중/종료 전환
- 모집 관련 요소 표시·숨김
- 지표 정수 저장과 `숫자+` 표시
- 연혁 최신순·스크롤
- 활동 기록 작성·수정·삭제·상세 조회
- 세미나·해커톤 자료 작성·수정·삭제·상세 조회
- 대표 이미지와 갤러리 이미지 업로드·교체
- 상세 화면에서 목록 필터와 스크롤 위치 복원

### 16.2 두 번째 시행: 보안과 장애

- 비로그인·비관리자 쓰기 거부
- 관리자 RLS 허용
- secret key 미노출
- 잘못된 URL, 파일 형식, 파일 크기 거부
- Supabase 조회 실패 시 캐시와 기본 데이터 사용
- 저장 실패 시 기존 데이터 보존

### 16.3 세 번째 시행: 실제 운영

- GitHub Pages 저장소 하위 경로에서 직접 진입과 새로고침
- `/`, `/log/`, `/archive/`, `/log/?id=<slug>`, `/archive/?id=<slug>` 동작
- 데스크톱·모바일 레이아웃과 기존 공개 디자인 비교
- 키보드 로그인·편집·대화상자 조작
- 관리자 로그인부터 콘텐츠 공개까지 전체 운영 흐름
- 사용자 지정 도메인 전환 절차 검토

각 시행 뒤에 `발견된 문제`, `수정 내용`, `이전 시행과 달라진 점`, `남은 위험`을 기록하고 최종 비교표를 작성한다.

## 17. Claude Code 비판 검토 프롬프트

최종 구현 후 다음 내용을 포함한 독립 검토 프롬프트를 제출할 수 있게 텍스트를 제공한다.

- 기존 디자인과 공개 기능이 실제로 보존됐는지
- GitHub Pages 경로와 사용자 지정 도메인 전환이 안전한지
- Supabase Auth와 RLS에 권한 상승·비밀키 노출·무단 쓰기 취약점이 없는지
- 휴면·네트워크 오류·부분 저장 실패에서 데이터가 유실되지 않는지
- 관리자 편집 흐름이 1~6개월 간격의 비개발자 운영에 충분히 단순한지
- 불필요한 추상화·의존성·중복 코드가 추가되지 않았는지
- 발견 사항을 심각도, 근거 파일·줄, 재현 방법, 최소 수정안으로 보고하도록 요청

## 18. 완료 기준

- 공개 사용자는 현재 디자인과 기능을 그대로 이용한다.
- 관리자는 현재 페이지에서 로그인하고 모든 요청 콘텐츠를 관리한다.
- 모집 종료 시 모집 관련 UI가 숨겨지고 종료 안내 배너만 보인다.
- 모집 중에는 설정한 기수·문구·폼 URL이 모든 모집 요소에 일관되게 반영된다.
- 홈 지표는 관리자 입력 정수를 항상 `숫자+`로 표시한다.
- 연혁은 최신 항목부터 보이며 제한 높이에서 스크롤된다.
- 활동 기록, 세미나 자료, 해커톤 결과물은 각각 직접 진입 가능한 상세 화면을 제공한다.
- 해커톤 상세 화면은 제공된 HTML의 콘텐츠 순서와 시각 체계를 따르며 관리자에게만 편집 컨트롤을 제공한다.
- 활동 기록과 아카이브는 실제 게시글·대표 이미지·갤러리·외부 결과물 링크를 지원한다.
- DB와 Storage 쓰기는 관리자만 가능하다.
- Supabase 조회 실패가 공개 페이지 전체 실패로 이어지지 않는다.
- GitHub Pages 기본 주소와 추후 `opt.it.kr`에서 동작한다.
- 세 차례 검증 비교 보고서와 Claude Code 비판 프롬프트가 제공된다.
